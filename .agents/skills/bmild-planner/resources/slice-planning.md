# Slice Planning

Create or revise lightweight Slices only when explicitly requested. Use settled contracts to make smaller development sessions independently understandable and reviewable. Advisory sequencing without persistent Slices belongs to Delivery Strategy.

## Additional Context

Reload the initiative registry, authorized outcome and coverage in `verification-matrix.md`, relevant live source contracts, and any existing `slices.md` and affected Slice records. Inspect implementation and integration boundaries for real dependencies. Use `assets/slices-template.md` and `assets/slice-template.md`; load the matrix template only when a parent outcome is missing.

## Global Directives

- **Close gaps in-session.** Any instruction below to route, defer to another owner, enqueue a handoff, or enter Course-Correction first invokes this skill's `references/gap-resolution.md`. Persist `H-###` only when the episode genuinely leaves the session; after resolution, re-read changed contracts and resume this mode.

- **Scope and readiness.** Plan the requested phase only; future-phase planning requires an explicit request and conveys no execution authority. Establish sufficient intent, observable acceptance, usable constraints, and proof. Resolve genuine source gaps with their owners; no mandatory artifact combination or new design gate.
- **Boundaries with a purpose.** Split for dependency safety, risk isolation, or useful acceptance checkpoints. Include necessary implementation guidance where another context would otherwise lose a constraint; leave task order, private design, and file choices to Alex. Do not copy specifications, predict file inventories, forecast effort, or budget tokens.
- **Stable identity.** Continue existing `slice-<N>.md` numbering using the next unused number across live and archived records; never renumber or reuse an ID. Every Slice links its parent `O-###`. Do not mint an outcome merely for each Slice. Create a missing outcome only from separate authorized scope and update its Outcome Index and rollup activation.
- **Boundary revisions.** Sonia owns acceptance boundaries and dependencies. Preserve completed evidence and historical records; mark only affected current proof pending when a boundary changes. Route commitment changes to their existing owners. Coupled consequential scope/sequencing/proof changes use user-authorized Course-Correction; routine Slice boundary repair within settled scope needs no new product approval.
- **One evidence authority.** The matrix owns implementation and independent evidence; Slice records and registries project it. Sonia plans, Alex implements, and only Rahat accepts and archives. Every Slice passing still requires current source coverage and integrated outcome verification.

## Tasks

- [ ] Step 1: Resolve requested decomposition or revision, parent outcome, phase authorization, and settled source boundaries. Ask only for genuinely missing scope or decisions.
- [ ] Step 2: Define useful Slice acceptance boundaries and explicit dependencies. Check source coverage, gaps/overlap, dependency cycles, and first eligible work. Link deferred and integrated obligations under the parent outcome rather than pretending a Slice list proves completeness.
- [ ] Step 3: Write or update `slices.md` and affected `slice-<N>.md` from the lean templates. Include parent, source links, acceptance/exclusions, prerequisites, necessary implementation guidance, and continuation links. Preserve accepted history; no copied specs, estimates, or predicted reads/edits.
- [ ] Step 4: Add Slice references and planned proof under the existing parent outcome. Register new artifacts as live, restore repaired artifacts from stale to live, and record changed boundaries with provenance. Do not overwrite review verdicts or archive Slices. Mark affected evidence pending and link any genuinely asynchronous obligation.
- [ ] Step 5: Close — identify the named or sole next eligible Slice and a Slice-Dev continuation. If multiple candidates remain equally eligible, say so; do not choose arbitrarily. Planning alone does not authorize implementation or a series.

## Definition of Done

- Requested Slices cover settled authorized scope with meaningful boundaries and satisfiable dependencies.
- Existing numbering, parent outcome identity, source links, and acceptance ownership preserved.
- Matrix carries proof and final integration obligations; Slice status is a projection, not a competing acceptance record.
- Implementation choices remain delegated and continuation is usable without a planning relay.
